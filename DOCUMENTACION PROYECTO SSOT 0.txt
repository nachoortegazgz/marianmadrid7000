## 0.4 · OBJETIVOS PRINCIPALES

### 0.4.1 Gestión de reservas online (Wix App Custom)

El motor de reservas es una **implementación custom sobre Wix Bookings V2** que extiende las capacidades nativas de Wix para soportar el modelo de negocio específico de Marian Madrid.

**Arquitectura de tres capas**:

| Capa | Módulo | Responsabilidad |
|---|---|---|
| Disponibilidad | `reservas.web.js` | Consulta Wix Bookings V2, construcción de slots duales, balanceo, caché |
| Orquestación | `bookingSaga.js` | Saga compensable, locks, idempotencia, creación paralela F1+F2 |
| Primitivas | `bookingCore.js` | Acceso a Wix Bookings V2, locks, transacciones, persistencia CitasF2 |

**Flujo de reserva**:

```
Cliente → getAvailableDays() → getCertifiedDualSlots() → executeBookingSaga()
         → [LockSlots] → [CreateBookings F1+F2] → [CreateCheckout / ConfirmPresencial]
         → persistBooking(CitasF2) → completeTransaction → unlock → invalidateCache
```

### 0.4.2 Tipos de servicios

| Tipo | Descripción | Campos clave en ServiciosCatalogo |
|---|---|---|
| Servicio simple | Una sola fase, una profesional | `serviceType: SIMPLE`, `allowCombine: false` |
| Servicio dual con gap | F1 (aplicación) → exposición → F2 (aclarado) | `serviceType: DUAL`, `allowCombine: true`, `linkedPhases`, `phase1Duration`, `exposureDuration`, `phase2Duration` |

**Modelo de servicio dual**:

```
F1 (Aplicación)  →  Gap/Exposición  →  F2 (Aclarado/Matizado)
phase1Duration       exposureDuration      phase2Duration
    ██████████░░░░░░░░░░░░░░░░░░░░░░░████████████
    │← Profesional ocupada →│← Libre →│← Ocup. →│
```

Durante el gap, la profesional queda liberada y puede atender otros servicios simples. El slot de F2 llega al final del gap.

**Complementos (addons)**: Servicios adicionales opcionales vinculados a un servicio principal. Se almacenan en `ComplementosCatalogo` y se vinculan vía `addOnOptions` (MULTI_REF).

### 0.4.3 Gestión del negocio según normativa y registros

**Ruta canónica de toda operación económica**:

```
Evento Wix o acción autorizada
    ↓
Validación de permisos e idempotencia
    ↓
Recálculo servidor (importes, impuestos, stock)
    ↓
Registro en ledger fiscal (MovimientosCaja)
    ↓
Registro contable (AsientosContables + LineasAsientoContable)
    ↓
Registro de auditoría (MmAuditLog + EventosSistemaFacturacion)
    ↓
Exportación documental al contable
```

## 0.5 · DIRECTRICES DE CALIDAD DE CÓDIGO Y BUENAS PRÁCTICAS

### 0.5.1 Criterio de código óptimo (DIRECTRICES V19 §1)

El código se considera óptimo y final **solo si cumple simultáneamente**:

| Dimensión | Criterio de aceptación |
|---|---|
| **Funcional** | Los flujos esenciales finalizan con resultado verificable, sin duplicados ni estados incongruentes |
| **Fiable** | Los errores parciales activan compensación, liberación de locks, persistencia coherente y respuestas seguras |
| **Simple** | Cada responsabilidad tiene un módulo propietario; no se duplican reglas, constantes, flujos de creación ni lógica de autorización |
| **Compatible con Wix** | Respeta contratos de Wix Bookings V2, Wix eCommerce, Wix Payments/Cashier, Wix Data, Wix Members, Wix Secrets |
| **Evolucionable** | Toda actualización del SDK se valida contra documentación oficial, contrato existente, pruebas y Local Editor antes de publicación |

> **La condición se demuestra con evidencia de pruebas** (locales, Local Editor, preview y sandbox del proveedor de pagos), **no por documentación o revisión estática aislada**.

### 0.5.2 Convenciones de código (DIRECTRICES V19 §3.2)

| Regla | Implementación |
|---|---|
| Funciones internas | Prefijo `_` |
| Web Methods | Permisos y rate limiting en el borde; funciones internas no reimplementan RBAC |
| Constantes | Importadas de `public/mmUtils.js` y `backend/internalConfig.js` |
| Secretos | Exclusivamente desde Wix Secrets Manager |

## 0.10 · NORMAS GENÉRICAS ANTI-SUPOSICIONES

### 0.10.1 Principio fundamental

> **Ninguna afirmación técnica es válida sin evidencia verificable.** El agente no puede asumir, inferir ni extrapolar comportamiento del código, de las APIs Wix, de las colecciones CMS ni de la normativa legal sin verificación directa.

### 0.10.2 Reglas anti-suposiciones

| ID | Regla | Implementación |
|---|---|---|
| AS-01 | No asumir que una función existe | Verificar con grep o lectura del archivo |
| AS-02 | No asumir que un campo existe en una colección | Verificar contra SSOT.json o Esquema CMS |
| AS-03 | No asumir que una API Wix se comporta de cierta forma | Consultar documentación oficial vigente |
| AS-04 | No asumir que un hook está activo | Verificar en `data.js` y probar con inserción real |
| AS-05 | No asumir que un test pasa | Ejecutar el test y presentar resultado |
| AS-06 | No asumir que un despliegue es seguro | Verificar con Local Editor y preview |
| AS-07 | No asumir cumplimiento legal | Requerir validación externa documentada |
| AS-08 | No asumir que un cambio es retrocompatible | Verificar con tests de regresión |
| AS-09 | No asumir que un secreto está configurado | Verificar en Wix Secrets Manager |
| AS-10 | No asumir que un índice existe | Verificar en el panel de Wix Data |
| AS-11 | No asumir que un enum tiene ciertos valores | Verificar en `internalConfig.js` |
| AS-12 | No asumir que un módulo puede escribir en una colección | Verificar matriz de acceso a colecciones |

### 0.10.3 Protocolo ante incertidumbre

| Situación | Acción |
|---|---|
| Información no disponible en fuentes SSOT | Marcar como `PENDIENTE DE VERIFICACIÓN` y solicitar aclaración |
| Contradicción entre fuentes | Documentar la contradicción y aplicar jerarquía de prevalencia |
| Comportamiento no determinista | Diseñar test reproducible antes de continuar |
| API Wix sin documentación clara | Marcar como `RIESGO DE INTEGRACIÓN` y diseñar fallback |

## 0.12 · FORMATO DE CÓDIGO CON HISTORIAL/INVENTARIO

### 0.12.1 Regla de inventario inicial

> **Todo archivo de código debe comenzar con un bloque de inventario** que identifique el módulo, su versión, sus funciones exportadas y su historial de cambios. Esto evita la pérdida de código durante refactorizaciones y permite trazabilidad.

### 0.12.2 Formato del bloque de inventario

```javascript
/**
 * ============================================================================
 * MODULO: backend/booking/bookingSaga.js
 * VERSION: v5002.6
 * SSOT: SSOT CONSOLIDADO v5002.6 | ESQUEMA CMS v5002.5 | DOSSIER RESERVAS v0609
 * MISION: Orquestador transaccional. Saga compensable para reservas simples y duales.
 * ============================================================================
 * INVENTARIO DE FUNCIONES:
 *   [EXPORT] _normalizePersistedMeta(meta)
 *   [EXPORT] _resolveStablePairToken({...})
 *   [EXPORT] _extractCheckoutId(checkoutSession)
 *   [EXPORT] _bestEffortUnlockAll(lockKeys, lockOwnerId)
 *   [CLASS]  SagaStep
 *   [CLASS]  BookingSagaOrchestrator
 *   [EXPORT] executeBookingSaga(unsafePayload)
 * ============================================================================
 * DEPENDENCIAS:
 *   - backend/internalConfig.js (COLLECTIONS, CONCURRENCY, TIMEOUTS)
 *   - backend/booking/bookingCore.js (primitivas atómicas)
 *   - backend/responseUtils.js (AppError, successResponse)
 *   - public/mmUtils.js (makeTraceId)
 * ============================================================================
 * COLECCIONES QUE ESCRIBE: CitasF2, BookingTransactions, SlotLocks,
 *                           CompensacionesPendientes, DualSlotCache
 * COLECCIONES QUE LEE: ServiciosCatalogo, MapaStaff
 * ============================================================================
 * HISTORIAL DE CAMBIOS:
 *   v5002.6 | 2026-09-14 | Consolidación SSOT. Sin cambios funcionales.
 *   v5002.5 | 2026-09-10 | Fix S-01: linkedPhases como fuente primaria.
 *   v5002.3 | 2026-09-06 | Versión inicial del dossier.
 * ============================================================================
 */
```

### 0.12.3 Reglas del inventario

| Regla | Descripción |
|---|---|
| INV-01 | Todo archivo de módulo debe tener el bloque de inventario |
| INV-02 | El inventario lista TODAS las funciones exportadas y clases |
| INV-03 | El inventario lista las dependencias de importación |
| INV-04 | El inventario lista las colecciones que escribe y lee |
| INV-05 | El historial registra cada cambio con versión, fecha y descripción |
| INV-06 | El inventario se actualiza en cada refactorización |

## 0.14 · CORRECCIONES Y COMPARATIVAS CON VERSIONES SUSTITUIDAS

### 0.14.1 Principio de verificación por comparativa

> **Toda corrección debe demostrar que el estado nuevo es estrictamente mejor que el estado anterior.** No se acepta una corrección que introduzca regresiones sin justificación explícita.

### 0.14.2 Formato de comparativa

| Aspecto | Versión anterior | Versión nueva | Verificación |
|---|---|---|---|
| Función X | Comportamiento anterior | Comportamiento nuevo | Test que lo demuestra |
| Campo Y | Tipo/valor anterior | Tipo/valor nuevo | Consulta CMS |
| Hook Z | No existía | Implementado | Test de inmutabilidad |
| Constante W | Valor anterior | Valor nuevo | Test unitario |

### 0.14.3 Reglas de corrección

| Regla | Descripción |
|---|---|
| CORR-01 | Toda corrección identifica el hallazgo que la motiva |
| CORR-02 | Toda corrección presenta el estado anterior y el estado nuevo |
| CORR-03 | Toda corrección incluye el test que verifica la mejora |
| CORR-04 | Toda corrección actualiza el inventario del módulo |
| CORR-05 | Toda corrección registra la versión en el historial |
| CORR-06 | Una corrección no puede eliminar funcionalidad sin justificación |
| CORR-07 | Una corrección no puede introducir deuda técnica nueva |
